1. INTRODUCCIÓN Y CONTEXTO DEL ALCANCE ACTUALIZADO
====================================================================================================
El presente documento consolida la línea base de requerimientos de ingeniería de software para el 
desarrollo del Sistema de Gestión Optométrica (SGO v2.0). A diferencia de las versiones preliminares 
acotadas a un MVP básico, el presente instrumento integra formalmente:

1. Facturación Electrónica Nativa con el Servicio de Rentas Internas (SRI):
   - Soporte para emisión de Facturas XML bajo el esquema oficial v1.1.0 (XSD).
   - Generación algorítmica de Clave de Acceso única de 49 dígitos con ponderación Módulo 11.
   - Firma criptográfica avanzada XAdES-BES Enveloped mediante certificados digitales PKCS#12 (.p12/.pfx).
   - Comunicación asíncrona mediante Web Services SOAP hacia los endpoints de Recepción y Autorización.
   - Generación automatizada de RIDE en PDF con código de barras Code128 y despacho por correo SMTP.

2. Componente de Innovación Tecnológica: Asistente Inteligente Operativo ("Chatbot con los Datos"):
   - Interfaz conversacional en lenguaje natural integrada en el Dashboard del sistema.
   - Enrutador determinístico de intenciones (Intent Router) para ventas, inventarios y taller.
   - Mecanismo de seguridad Read-Only Guard: ejecución exclusiva bajo usuario SQL con privilegios 
     GRANT SELECT en PostgreSQL, imposibilitando cualquier mutación, borrado o inyección de datos.
   - Filtrado estricto por roles (RBAC) en respuestas para evitar fuga de información confidencial.
   - Resiliencia híbrida con conmutación autónoma en red local LAN offline sin depender de internet.

3. Stack Tecnológico Seleccionado:
   - Backend Transaccional Central: PHP 8.2+ con Framework Laravel 11 (API RESTful modular).
   - Microservicio de Facturación y Criptografía: Node.js 20 LTS (TypeScript, node-forge, xml-crypto).
   - Base de Datos: PostgreSQL 15+ (cumplimiento ACID, triggers PL/pgSQL y audit_logs inmutable).
   - Frontend de Usuario: React 18+ (TypeScript, Vite, TailwindCSS y soporte PWA).
   - Despliegue: Contenedores Docker multi-etapa orquestados con Docker Compose.

2.1 MÓDULO 1: AUTENTICACIÓN Y CONTROL DE ACCESO GRANULAR (M1)
----------------------------------------------------------------------------------------------------

[RF-01] Control de Acceso Basado en Roles (RBAC)
- Tipo: Requisito de Seguridad / Autorización
- Prioridad: Alta / Esencial (Must Have)
- Fuente: Entrevistas 1 y 2 / Anteproyecto ESPOCH
- Módulo: M1 (Seguridad y Acceso)
- S-Tag: [S-TAG-AUTH-01]
- Descripción: El sistema debe autenticar a los operadores del establecimiento y restringir el acceso 
  a módulos, vistas de interfaz y endpoints de la API REST según tres perfiles formales:
  * Administrador: Acceso total a configuración, catálogos, auditoría forense, caja y fiscalidad.
  * Optometrista: Acceso a pacientes, consultas visuales, refracción, recetas y órdenes de taller.
  * Asistente Comercial: Acceso a registro demográfico, ventas, cobro de anticipos, arqueo y entregas.
- Entradas: Nombre de usuario / correo institucional y contraseña en texto plano.
- Proceso: Verificación criptográfica de contraseña mediante hash bcrypt con factor de coste 12; 
  validación de estado activo del usuario; generación de token JWT firmado digitalmente con claims 
  de rol y permisos específicos; intercepción por middleware en frontend y backend ante cada petición.
- Salidas: Sesión autorizada con token JWT o código HTTP 403 Forbidden ante intentos no autorizados.
- Criterio de Verificación: Intentos de navegación manual a URLs administrativas desde cuentas de 
  asistente u optometrista son bloqueados y registrados en auditoría.

[RF-02] Gestión Segura de Sesiones y Expiración por Inactividad
- Tipo: Requisito de Seguridad / Sesiones
- Prioridad: Alta / Esencial (Must Have)
- Fuente: Entrevista 2 / Decisiones de Ciberseguridad ESPOCH
- Módulo: M1 (Seguridad y Acceso)
- S-Tag: [S-TAG-AUTH-02]
- Descripción: El sistema debe gestionar las sesiones web mediante tokens JWT firmados (SHA-256), 
  forzando la expiración y revocación automática de la sesión tras 20 minutos continuos de inactividad 
  de teclado o mouse en el cliente, protegiendo las estaciones ante descuidos del personal.
- Entradas: Detección continua de eventos del DOM (mousemove, keydown) o temporizador de inactividad.
- Proceso: El cliente computa el tiempo sin interacción; al transcurrir 20 minutos sin eventos, 
  solicita la inclusión del token en la lista negra (blacklist) del servidor y purga el token de memoria.
- Salidas: Destrucción de la sesión en cliente y redirección forzosa al Login con notificación visual.
- Criterio de Verificación: Una estación sin actividad durante 20:01 minutos queda bloqueada y exige 
  re-autenticación obligatoria.

2.2 MÓDULO 2: GESTIÓN DEMOGRÁFICA DE PACIENTES (M2)

[RF-03] Validación Algorítmica de Cédula Ecuatoriana (Módulo 10)
- Tipo: Requisito Funcional / Integridad de Datos
- Prioridad: Alta / Esencial (Must Have)
- Fuente: Registro Civil del Ecuador / plaDesarrolloRequisitos
- Módulo: M2 (Gestión de Pacientes)
- S-Tag: [S-TAG-INT-01]
- Descripción: El sistema debe validar automáticamente la estructura formal y el dígito verificador 
  de las cédulas de identidad ecuatorianas mediante el algoritmo matemático de Módulo 10, impidiendo 
  el ingreso de documentos ficticios o duplicados en el padrón de pacientes.
- Entradas: Número de identificación (10 dígitos numéricos).
- Proceso: Comprobación de longitud exacta; verificación del código de provincia (01 a 24 o 30); 
  multiplicación de los primeros 9 dígitos por coeficientes alternados [2, 1, 2, 1, 2, 1, 2, 1, 2] con 
  resta de 9 a productos >= 10; suma total; cálculo de residuo frente a decena superior y cotejo estricto 
  con el décimo dígito.
- Salidas: Estado de validación (Válido / Inválido) con alerta visual en la interfaz en tiempo real.
- Criterio de Verificación: El botón de guardado permanece deshabilitado si la cédula no supera el Módulo 10.

[RF-04] Registro Demográfico y Ficha de Contacto Clínico
- Tipo: Requisito Funcional / Maestros
- Prioridad: Alta / Esencial (Must Have)
- Fuente: Entrevistas 1 y 2 / Formulario 024 MSP
- Módulo: M2 (Gestión de Pacientes)
- S-Tag: ---
- Descripción: El sistema debe registrar y administrar los datos demográficos completos del paciente: 
  Nombres completos, Apellidos, Tipo y Número de Documento, Fecha de Nacimiento (con cálculo dinámico 
  de edad cronológica), Ocupación (clave para ergonomía visual), Teléfono principal, Correo y Dirección.
- Entradas: Formulario demográfico completado por el operador.
- Proceso: Sanitización de entradas contra XSS; validación de unicidad de cédula en la tabla `pacientes`; 
  cálculo dinámico de edad en años, meses y días; persistencia transaccional con timestamp y usuario autor.
- Salidas: Ficha del paciente creada con identificador único de expediente clínico (UUID).
- Criterio de Verificación: Registro exitoso visible en el catálogo de pacientes y trazado en auditoría.

[RF-05] Búsqueda Indexada Multicriterio y Paginación Server-Side
- Tipo: Requisito Funcional / Usabilidad y Desempeño
- Prioridad: Alta / Esencial (Must Have)
- Fuente: Entrevistas 1 y 2 / Especificación v1.0
- Módulo: M2 (Gestión de Pacientes)
- S-Tag: [S-TAG-INT-01]
- Descripción: El sistema debe ofrecer un motor de búsqueda indexado que permita localizar pacientes 
  por Apellidos, Nombres, Cédula o Número de Historia Clínica con resultados paginados en el servidor.
- Entradas: Cadena de búsqueda (mínimo 2 caracteres) digitada en la barra de consulta.
- Proceso: Ejecución de consulta optimizada mediante índices B-Tree y trigram (pg_trgm) sobre campos clave; 
  paginación server-side mediante LIMIT y OFFSET (20 registros por página).
- Salidas: Listado interactivo paginado con tiempo de respuesta inferior a 300 milisegundos.
- Criterio de Verificación: Búsqueda instantánea demostrada con volumen superior a 10,000 registros.

[RF-06] Repositorio Digital de Adjuntos Clínicos y Archivos Externos
- Tipo: Requisito Funcional / Gestión Documental
- Prioridad: Media / Deseado (Should Have)
- Fuente: Entrevista 2 / plaDesarrolloRequisitos
- Módulo: M2 (Gestión de Pacientes)
- S-Tag: [S-TAG-INT-02]
- Descripción: El sistema debe permitir asociar a la ficha del paciente archivos digitalizados de estudios 
  oftalmológicos externos (topografías, retinografías, recetas de otros centros o informes) en formatos 
  PDF, PNG o JPEG, con límite de tamaño de 5 MB por archivo.

- Criterio de Verificación: Aislamiento del archivo contra descargas de usuarios no autenticados.

[RF-07] Validación Estricta de Rangos Dióptricos (OD/OI)
- Tipo: Requisito Funcional / Integridad Médica
- Prioridad: Alta / Esencial (Must Have)
- Fuente: Formulario 024 MSP / Entrevista 2
- Módulo: M3 (Historia Clínica)
- S-Tag: [S-TAG-INT-01]
- Descripción: El sistema debe validar de manera estricta que los parámetros de refracción ingresados 
  por el optometrista se ubiquen dentro de los rangos fisiológicos y técnicos válidos en pasos discretos 
  de 0.25 Dioptrías (D):
  * Esfera (Sph): -25.00 D a +25.00 D.
  * Cilindro (Cyl): -10.00 D a 0.00 D (notación negativa).
  * Eje (Axis): 0° a 180° (números enteros).
- Entradas: Valores numéricos de Esfera, Cilindro y Eje para Ojo Derecho (OD) y Ojo Izquierdo (OI).
- Proceso: Evaluación de expresiones regulares en cliente y constraints CHECK en PostgreSQL; rechazo 
  automático de cualquier valor fraccionario no múltiplo de 0.25 D.
- Salidas: Aceptación del valor o bloqueo visual del campo con borde rojo y mensaje de error específico.
- Criterio de Verificación: Imposibilidad física de persistir una graduación con decimales no estándar.

[RF-08] Formateo y Normalización Numérica Decimal Dióptrica
- Tipo: Requisito Funcional / Calidad de Datos
- Prioridad: Alta / Esencial (Must Have)
- Fuente: plaDesarrolloRequisitos / Práctica Optométrica
- Módulo: M3 (Historia Clínica)
- S-Tag: [S-TAG-INT-01]
- Descripción: El sistema debe normalizar y formatear automáticamente los valores dióptricos ingresados 
  añadiendo el signo correspondiente (+ o -) y dos posiciones decimales obligatorias (ej. el ingreso 
  de "2" se formatea como "+2.00"; "-1.5" se formatea como "-1.50").
- Entradas: Cadena numérica digitada por el profesional.
- Proceso: Función mutadora en backend y filtro en evento onBlur de React que parsea a punto flotante de 
  precisión fija y aplica máscara con signo explícito.
- Salidas: Valor estandarizado con formato exacto `+X.XX` o `-X.XX` persistido homogéneamente.
- Criterio de Verificación: Homogeneidad del 100% de registros en la base de datos relacional.

[RF-09] Notación Estándar de Cilindro Negativo (Transposición Óptica)
- Tipo: Requisito Funcional / Física y Algoritmos Ópticos
- Prioridad: Alta / Esencial (Must Have)
- Fuente: Formulario 024 MSP / Práctica Optométrica
- Módulo: M3 (Historia Clínica)
- S-Tag: ---
- Descripción: El sistema debe exigir el registro del astigmatismo en notación de cilindro negativo. Si el 
  optometrista ingresa una fórmula en cilindro positivo, el sistema proveerá una función automática 
  de transposición aplicando la fórmula de óptica oftálmica:
  * Esfera_nueva = Esfera_original + Cilindro_original
  * Cilindro_nuevo = -Cilindro_original
  * Eje_nuevo = (Eje_original +/- 90°) mod 180°
- Entradas: Fórmula con valor de cilindro positivo digitada accidentalmente.
- Proceso: Detección de signo positivo en Cyl; cálculo algebraico de nueva esfera, inversión de signo 
  del cilindro y rotación ortogonal del eje con normalización entre 0° y 180°.
- Salidas: Fórmula transpuesta a cilindro negativo con aceptación del usuario.
- Criterio de Verificación: Conversión matemática exacta conforme a las leyes de la física óptica.

[RF-10] Validación de Distancia Nasopupilar (DNP) y Altura Focal
- Tipo: Requisito Funcional / Centrado Óptico
- Prioridad: Alta / Esencial (Must Have)
- Fuente: Entrevistas 1 y 2 / Normas de Biselado
- Módulo: M3 (Historia Clínica)
- S-Tag: [S-TAG-INT-01]
- Descripción: El sistema debe exigir y validar el registro de la Distancia Nasopupilar (DNP) individual 
  por ojo (OD y OI) en un rango fisiológico de 20.0 mm a 40.0 mm (o DIP total de 40 a 80 mm), y la 
  Altura Focal en milímetros cuando se seleccionen lentes bifocales o multifocales progresivos.
- Entradas: Valores milimétricos de DNP OD, DNP OI y Altura Focal.
- Proceso: Verificación de límites fisiológicos; suma automática de DIP = DNP_OD + DNP_OI; campo Altura 
  marcado como requerido si el tipo de luna seleccionado es progresivo o bifocal.
- Salidas: Parámetros validados y consolidados para la orden técnica de taller.
- Criterio de Verificación: Alerta bloqueante si se ingresa una DNP fuera del rango 20.0 - 40.0 mm.

[RF-11] Regla Óptica de Adición Esférica y Simetría Binocular (OD = OI)
- Tipo: Requisito Funcional / Regla Médica de Presbicia
- Prioridad: Alta / Esencial (Must Have)
- Fuente: Entrevista 2 / Guías Clínicas de Refracción
- Módulo: M3 (Historia Clínica)
- S-Tag: [S-TAG-INT-02]
- Descripción: El sistema debe controlar que el valor de Adición (Add) para pacientes présbitas se 
  encuentre en el rango de +0.75 D a +4.00 D en pasos de 0.25 D, y forzar la regla de simetría binocular 
  médica obligatoria (Add_OD = Add_OI), replicando el valor de un ojo en el otro para prevenir astenopia.
- Entradas: Valor de Adición seleccionado o digitado en el ojo derecho.
- Proceso: Validación de rango positivo; actualización reactiva automática en el campo del ojo izquierdo; 
  bloqueo de edición asimétrica salvo excepción médica documentada en observaciones clínicas.
- Salidas: Ambos ojos con idéntico valor de Adición para visión cercana.
- Criterio de Verificación: Igualdad matemática comprobada en la tupla de base de datos.

[RF-12] Comparativa Dióptrica Evolutiva y Análisis de Progresión

[RF-15] Inmutabilidad de Consultas Previas y Preservación Histórica (Soft-Delete)
- Tipo: Requisito de Seguridad / Integridad Forense

- Módulo: M3 (Historia Clínica)

- Criterio de Verificación: Comprobación de existencia de tuplas históricas intactas en PostgreSQL.

[RF-16] Aislamiento de Datos Clínicos y Cumplimiento LOPDP en Órdenes de Taller

3.1 SEGURIDAD DE LA INFORMACIÓN (AUTENTICIDAD, CONFIDENCIALIDAD, INTEGRIDAD Y NO REPUDIO)
----------------------------------------------------------------------------------------------------

[RNF-01] Control de Acceso Estricto y Principio de Menor Privilegio (RBAC)
- Subcaracterística ISO 25010: Autenticidad y Autorización
- Etiqueta de Seguridad: [S-TAG-AUTH-01]
- Métrica / Criterio: El 100% de las rutas de interfaz y endpoints de la API deben validar el rol y los 
  claims del token JWT. La tasa de acceso indebido permitida a recursos no autorizados es 0.00%.

[RNF-02] Cifrado Robusto de Credenciales y Sesiones Web
- Subcaracterística ISO 25010: Confidencialidad
- Etiqueta de Seguridad: [S-TAG-AUTH-02]
- Métrica / Criterio: Las contraseñas deben cifrarse con hash irreversible bcrypt (factor de coste 12). 
  Los tokens JWT deben firmarse con HMAC-SHA256 utilizando una clave secreta de 256 bits custodiada 
  en variables de entorno seguras del servidor, con tiempo de expiración fijado en 20 minutos.

[RNF-03] Validación Dióptrica a Nivel de Motor de Base de Datos
- Subcaracterística ISO 25010: Integridad de Datos
- Etiqueta de Seguridad: [S-TAG-INT-01]
- Métrica / Criterio: La base de datos PostgreSQL debe implementar restricciones CHECK para impedir 
  que valores de Esfera fuera de [-25.00, +25.00], Cilindro fuera de [-10.00, 0.00] o Eje fuera de [0, 180] 
  puedan ser insertados mediante inyecciones o fallas en el cliente.

[RNF-04] Transaccionalidad ACID en Operaciones de Caja e Inventario
- Subcaracterística ISO 25010: Integridad y Fiabilidad
- Etiqueta de Seguridad: [S-TAG-INT-02]
- Métrica / Criterio: Toda venta, cobro de anticipo, anulación o ajuste de stock debe ejecutarse dentro 
  de un bloque transaccional atómico (`BEGIN ... COMMIT / ROLLBACK`) con nivel de aislamiento READ COMMITTED. 
  La tasa de inconsistencias contables tolerada en caja es 0.00%.

[RNF-05] Inmutabilidad Histórica de Atenciones Médicas
- Subcaracterística ISO 25010: Integridad y Responsabilidad
- Etiqueta de Seguridad: [S-TAG-INT-03]
- Métrica / Criterio: Se prohíbe la sentencia UPDATE sobre historias clínicas cerradas. La corrección 
  de errores materiales solo se permite mediante borrado lógico (`soft-delete`) dejando constancia del 
  usuario responsable, timestamp y motivo formal en la bitácora inmutable.

[RNF-06] Bitácora Inmutable de Auditoría Forense (Audit Logs)
- Subcaracterística ISO 25010: Responsabilidad y Trazabilidad (No Repudio)
- Etiqueta de Seguridad: [S-TAG-RES-01]
- Métrica / Criterio: Cada acción crítica (creación de paciente, cambio de estado de taller, cobro, 
  anulación y consulta IA) debe registrarse automáticamente en la tabla `audit_logs` con `user_id`, `ip_address`, 
  `accion`, `tabla_afectada`, `valores_anteriores (JSONB)`, `valores_nuevos (JSONB)` y marca temporal del servidor.

[RNF-10] Custodia Criptográfica Segura de Certificados de Firma Electrónica (.p12)
- Subcaracterística ISO 25010: Confidencialidad y No Repudio
- Etiqueta de Seguridad: [S-TAG-AUTH-03]
- Métrica / Criterio: El certificado digital PKCS#12 (.p12) y su contraseña de firma deben custodiarse 
  cifrados en el servidor mediante algoritmo AES-256-GCM. La clave maestra de cifrado no debe estar hardcodeada

[RNF-11] Aislamiento Categórico de Solo Lectura para el Asistente IA
- Subcaracterística ISO 25010: Integridad y Seguridad
- Etiqueta de Seguridad: [S-TAG-INT-06]
- Métrica / Criterio: El microservicio del chatbot debe conectarse a PostgreSQL mediante un usuario técnico 
  con privilegio exclusivo `GRANT SELECT`. La ejecución de comandos DDL o DML de mutación es bloqueada 
  en el 100% de los casos tanto a nivel de middleware como a nivel de base de datos.
