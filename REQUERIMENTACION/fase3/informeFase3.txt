1. INTRODUCCIÓN, OBJETIVOS Y MARCO NORMATIVO DE LA FASE 3
================================================================================

1.1 PROPÓSITO Y ARTICULACIÓN CON LAS FASES ANTECESORAS
El presente informe formaliza la ejecución de la FASE 3: ESPECIFICACIÓN Y MODELADO 
FORMAL DE REQUISITOS Y CASOS DE USO (UML) para el Sistema Informático de Gestión 
Clínica y Comercial Optométrica (SGO). Esta fase transforma la materia prima de la 
Fase 1 (`informeFase1.txt`), el alcance delimitado en `Alcance.txt` y la priorización y 
reglas de negocio aprobadas en la Fase 2 (`informeFase2.txt`), en especificaciones 
técnicas rigurosas, atómicas, verificables y listas para guiar el diseño arquitectónico 
y la construcción en Sprints de Scrum.

1.2 ESTÁNDARES RECTORES
La especificación se elabora bajo la convergencia de cuatro marcos técnicos:
1. IEEE Std 830-1998: Estructuración formal de la Especificación de Requisitos de Software (SRS).
2. ISO/IEC 25010:2023: Modelo de calidad del producto de software, enfocado en la característica 
   de Seguridad (subcaracterísticas: Autenticidad, Integridad y Responsabilidad).
3. UML 2.5 (Unified Modeling Language): Modelado gráfico y textual de Casos de Uso del 
   Sistema (CUS), conforme a la teoría consolidada en `CasosUsoTeoria.txt`.
4. Secure Scrum (Pohl y Hof, 2015): Integración transversal de requisitos de seguridad 
   mediante etiquetas semánticas (S-Tags).

1.3 CRITERIOS DE CALIDAD DE LA ESPECIFICACIÓN
Cada requisito especificado en esta fase cumple rigurosamente con los atributos de:
- Atomicidad: Cada requerimiento expresa una única exigencia comprobable.
- No ambigüedad: Redacción unívoca y estandarizada entre clínicos e ingenieros.
- Verificabilidad: Posibilidad de diseñar un caso de prueba finito con resultado binario (pasa/no pasa).
- Trazabilidad: Identificador único que enlaza su fuente original con su caso de uso y caso de prueba.

2.1 MÓDULO 1: AUTENTICACIÓN Y GESTIÓN DE USUARIOS (M1)
--------------------------------------------------------------------------------

[RF-01] Control de Acceso Basado en Roles (RBAC)
- Módulo: M1 - Autenticación y Usuarios | Prioridad MoSCoW: Must Have
- Actor Primario: Administrador / Propietario (ACT-01).
- Descripción: El sistema debe restringir el acceso a módulos, vistas y endpoints de API 
  conforme a tres roles definidos: Administrador/Propietario (acceso total clínico, 
  comercial y de configuración), Optometrista (acceso a pacientes, historias clínicas, 
  órdenes de taller y emisión de recetas) y Asistente/Vendedor (acceso a registro demográfico 
  de pacientes, ventas, cobros de mostrador y arqueo de caja).
- Precondición: El usuario se encuentra registrado en el padrón de operadores del sistema.
- Entradas: Identificador de usuario, rol seleccionado, credenciales de autenticación.
- Lógica / Regla de Negocio: Aplicar middleware de autorización en cada solicitud HTTP; 
  si un usuario con rol Asistente intenta acceder a la ruta `/api/v1/historias-clinicas`, 
  el sistema debe responder con código HTTP 403 Forbidden y registrar intento no autorizado.
- Salida / Postcondición: Redirección al panel del rol correspondiente o denegación de acceso.
- S-Tag Asociado: [S-TAG-AUTH-01] [S-TAG-AUTH-02]

[RF-02] Gestión Segura de Sesiones y Expiración por Inactividad
- Módulo: M1 - Autenticación y Usuarios | Prioridad MoSCoW: Must Have
- Actor Primario: Todos los Actores del Sistema (ACT-01, ACT-02, ACT-03).
- Descripción: El sistema debe gestionar sesiones de usuario mediante tokens de acceso 
  JWT (JSON Web Tokens) firmados criptográficamente. La sesión debe expirar de forma 
  automática tras 20 minutos de inactividad del usuario (falta de interacción en mouse/teclado).
- Precondición: Sesión iniciada y token activo en almacenamiento de memoria del cliente.
- Entradas: Detección de inactividad temporal o solicitud explícita de cierre de sesión.
- Lógica / Regla de Negocio: Al detectar 20 minutos sin peticiones o eventos de UI, el 
  cliente debe purgar el token localmente e invalidarlo en el backend, redirigiendo a la pantalla de Login.
- Salida / Postcondición: Sesión revocada, token invalidado y bloqueo inmediato de la interfaz.
- S-Tag Asociado: [S-TAG-AUTH-03] [S-TAG-AUTH-04]

2.2 MÓDULO 2: GESTIÓN DE PACIENTES (M2)
--------------------------------------------------------------------------------

[RF-03] Registro Demográfico y Filiación del Paciente
- Módulo: M2 - Gestión de Pacientes | Prioridad MoSCoW: Must Have
- Actor Primario: Asistente (ACT-03) / Optometrista (ACT-02).
- Descripción: El sistema debe registrar y mantener los datos de filiación del paciente: 
  nombres completos, apellidos completos, número de cédula/pasaporte, número de teléfono 
  móvil, correo electrónico (opcional), fecha de nacimiento, sexo y ocupación/actividad visual.
- Precondición: Operador con sesión activa y privilegios de recepción o consulta.
- Entradas: Formulario de datos personales y demográficos.
- Lógica / Regla de Negocio: Validar que los nombres no contengan caracteres numéricos; 
  calcular automáticamente la edad cronológica en años a partir de la fecha de nacimiento.
- Salida / Postcondición: Registro de paciente insertado en la base de datos con ID único generado.
- S-Tag Asociado: [S-TAG-INT-02]

[RF-04] Manejo Flexible de Fichas para Pacientes Menores de Edad
- Módulo: M2 - Gestión de Pacientes | Prioridad MoSCoW: Should Have
- Actor Primario: Asistente (ACT-03) / Optometrista (ACT-02).
- Descripción: El sistema debe permitir abrir la ficha de atención clínica a nombre de un 
  paciente menor de edad (edad < 18 años) sin exigir de forma obligatoria que posea número 
  de cédula propio en el momento de la consulta, admitiendo asociar de forma opcional los 
  datos del representante o tutor legal.
- Precondición: Edad calculada menor a 18 años.
- Entradas: Nombres del menor, selector de "Sin cédula en el momento", cédula/nombre del tutor (opcional).
- Lógica / Regla de Negocio: Si no se ingresa cédula propia, el sistema genera un identificador 
  provisional único (prefijo `MEN-` + timestamp) para no trabar el flujo de consulta.
- Salida / Postcondición: Ficha pediátrica creada con identificador temporal válido.
- S-Tag Asociado: [S-TAG-INT-02]

[RF-05] Búsqueda Predictiva y Prevención de Cédulas Duplicadas
- Módulo: M2 - Gestión de Pacientes | Prioridad MoSCoW: Must Have
- Actor Primario: Asistente (ACT-03) / Optometrista (ACT-02).
- Descripción: El sistema debe implementar un validador algorítmico de módulo 10 para cédulas 
  de identidad de la República del Ecuador y una barra de búsqueda predictiva con autocompletado 
  en tiempo real por número de documento o apellidos, impidiendo registros duplicados.
- Precondición: Ingreso de al menos 3 caracteres en búsqueda o 10 dígitos en cédula.
- Entradas: Cadena de búsqueda alfanumérica o número de cédula en registro.
- Lógica / Regla de Negocio: Aplicar validación de provincia (01-24) y tercer dígito (< 6). 
  Si el número de cédula ya existe en la base de datos, el sistema bloquea el botón guardar 
  y despliega enlace directo al historial del paciente existente.
- Salida / Postcondición: Lista desplegable de coincidencias o mensaje de alerta de documento duplicado.
- S-Tag Asociado: [S-TAG-INT-02]

[RF-06] Carga y Almacenamiento Seguro de Adjuntos Clínicos Digitales
- Módulo: M2 - Gestión de Pacientes | Prioridad MoSCoW: Could Have
- Actor Primario: Optometrista (ACT-02).
- Descripción: El sistema debe permitir cargar y asociar a la ficha del paciente archivos 
  digitales de exámenes complementarios (topografías corneales, Pentacam, fotos de fondo 
  de ojo, retinografías) en formatos PDF, JPG y PNG con un tamaño máximo de 10 MB por archivo.
- Precondición: Ficha de paciente abierta en pantalla.
- Entradas: Archivo binario seleccionado desde el equipo local y descripción breve.
- Lógica / Regla de Negocio: Validar tipo MIME real en el backend; renombrar el archivo con 
  un hash criptográfico único (UUIDv4) y almacenarlo en directorio privado fuera del root web.
- Salida / Postcondición: Archivo almacenado y enlazado en la pestaña de historial clínico.
- S-Tag Asociado: [S-TAG-INT-02] [S-TAG-RES-01]

2.3 MÓDULO 3: HISTORIA CLÍNICA Y GRADUACIÓN (M3)
--------------------------------------------------------------------------------

[RF-07] Registro de Examen Refractivo Estándar Ojo Derecho (OD) y Ojo Izquierdo (OS)
- Módulo: M3 - Historia Clínica | Prioridad MoSCoW: Must Have
- Actor Primario: Optometrista (ACT-02).
- Descripción: El sistema debe registrar de forma independiente para el ojo derecho (OD) 
  y el ojo izquierdo (OS) los parámetros de la refracción: Esfera (+/-), Cilindro (-), 
  Eje angular (0°-180°), Adición (+), Distancia Pupilar (DP en mm), Altura focal (en mm) y Prismas.
- Precondición: Paciente seleccionado en consulta activa.
- Entradas: Valores numéricos de la refracción en formulario clínico.
- Lógica / Regla de Negocio: Aplicar validaciones según RN-CLI-02 y RN-CLI-03:
  * Esfera: $[-25.00, +20.00]$ D en pasos de $0.25$ D.
  * Cilindro: $[-10.00, 0.00]$ D en pasos de $0.25$ D (cilindros negativos obligatorios).
  * Eje: Entero entre $0^\circ$ y $180^\circ$. Si cilindro $\neq 0$, eje es obligatorio.
- Salida / Postcondición: Parámetros refractivos guardados y asociados a la consulta.
- S-Tag Asociado: [S-TAG-INT-01]

[RF-08] Aplicación Automática y Exigencia de Signo Positivo (+) en Adición
- Módulo: M3 - Historia Clínica | Prioridad MoSCoW: Must Have
- Actor Primario: Optometrista (ACT-02).
- Descripción: El campo de Adición (visión de cerca) debe forzar y exigir estrictamente el 
  signo positivo (+). Si el usuario digita un valor numérico sin signo (ej. "2.00"), el 
  sistema debe formatearlo y persistirlo automáticamente como "+2.00".
- Precondición: Ingreso de valor en el campo Adición.
- Entradas: Cadena numérica ingresada por el optometrista.
- Lógica / Regla de Negocio: Si el valor inicia con signo negativo (-), rechazar el dato con 
  mensaje de error clínico. Si no tiene signo, anteponer el signo (+). Rango: $[+0.75, +4.00]$ D en pasos de 0.25 D.
- Salida / Postcondición: Campo normalizado con signo (+) visible y almacenado.
- S-Tag Asociado: [S-TAG-INT-01]

[RF-09] Registro Estandarizado de Agudeza Visual Snellen Fraccionaria en Pies
- Módulo: M3 - Historia Clínica | Prioridad MoSCoW: Must Have
- Actor Primario: Optometrista (ACT-02).
- Descripción: El sistema debe permitir registrar la Agudeza Visual (AV) monocular (OD, OS) 
  y binocular (AO), tanto sin corrección (visión habitual) como con corrección (visión final), 
  para visión de lejos y de cerca, bajo la escala estándar Snellen fraccionaria en pies.
- Precondición: Consulta optométrica en curso.
- Entradas: Selección de lista desplegable con valores estándar Snellen: 20/20, 20/25, 20/30, 
  20/40, 20/50, 20/70, 20/100, 20/200, 20/400, Cuenta Dedos (CD), Percepción Luz (PL), No Percepción Luz (NPL).
- Lógica / Regla de Negocio: Validación de selección contra catálogo cerrado para evitar 
  notaciones erráticas de texto libre.
- Salida / Postcondición: Agudezas visuales guardadas en el registro del examen.
- S-Tag Asociado: [S-TAG-INT-01]

[RF-10] Captura de Parámetros Físico-Ópticos (Distancias y Alturas Nasopupilares)
- Módulo: M3 - Historia Clínica | Prioridad MoSCoW: Must Have
- Actor Primario: Optometrista (ACT-02) / Asistente (ACT-03).
- Descripción: El sistema debe capturar la Distancia Pupilar total (DP) o las Distancias 
  Nasopupilares monoculares (DNP derecha e izquierda) y las alturas focales pupilares (en mm) 
  para el correcto centrado de las lunas en el armazón.
- Precondición: Formulario de refracción o toma de medidas de montaje.
- Entradas: Valores enteros o decimales en milímetros (rango DP total: 45 mm a 75 mm; DNP: 22 mm a 38 mm).
- Lógica / Regla de Negocio: Validar que la suma de DNP derecha + DNP izquierda coincida 
  con una tolerancia de $\pm 1$ mm respecto a la DP total si ambas son ingresadas.
- Salida / Postcondición: Parámetros de centrado registrados para la orden de taller.
- S-Tag Asociado: [S-TAG-INT-01]

[RF-11] Parámetros Avanzados para Lentes Progresivos (Alta Gama)
- Módulo: M3 - Historia Clínica | Prioridad MoSCoW: Should Have
- Actor Primario: Optometrista (ACT-02).
- Descripción: El sistema debe permitir registrar de forma opcional las medidas morfológicas 
  del armazón para lentes progresivos/multifocales de alta gama: calibre horizontal (A), 
  calibre vertical (B), diagonal mayor (ED), puente (DBL) en milímetros, y los ángulos 
  especiales: ángulo pantoscópico (en grados) y ángulo panorámico de montura.
- Precondición: Selección de tipo de lente multifocal o progresivo.
- Entradas: Medidas A, B, ED, DBL en mm; ángulos en grados enteros.
- Lógica / Regla de Negocio: Habilitar los campos exclusivamente si el tipo de prescripción 
  lo demanda; almacenar valores validados en subtabla técnica de montura.
- Salida / Postcondición: Ficha técnica morfológica almacenada.
- S-Tag Asociado: [S-TAG-INT-01]

[RF-12] Comparativa Evolutiva Simultánea con Graduación Anterior en Pantalla
- Módulo: M3 - Historia Clínica | Prioridad MoSCoW: Must Have
- Actor Primario: Optometrista (ACT-02).
- Descripción: El sistema debe presentar en la misma pantalla de consulta una vista paralela 
  que contraste los valores de la refracción anterior del paciente (o la medida de su lente 
  actual) frente a los campos de la nueva refracción en proceso.
- Precondición: El paciente cuenta con al menos una consulta registrada en el historial.
- Entradas: ID del paciente seleccionado.
- Lógica / Regla de Negocio: Consultar el último registro refractivo histórico activo y 
  desplegarlo en modo de solo lectura en un panel adyacente para comparación visual inmediata.
- Salida / Postcondición: Visualización comparativa simultánea en la interfaz de usuario.
- S-Tag Asociado: [S-TAG-INT-03]

[RF-13] Registro de Anamnesis, Patologías Sistémicas y Diagnóstico CIE-10
- Módulo: M3 - Historia Clínica | Prioridad MoSCoW: Must Have
- Actor Primario: Optometrista (ACT-02).
- Descripción: El sistema debe registrar el motivo de consulta, antecedentes patológicos 
  personales/familiares (diabetes mellitus, hipertensión arterial, glaucoma, cataratas), 
  hallazgos biomicroscópicos y el diagnóstico optométrico codificado bajo el estándar internacional CIE-10.
- Precondición: Consulta optométrica en proceso.
- Entradas: Texto de anamnesis, checkboxes de patologías y buscador predictivo de códigos CIE-10.
- Lógica / Regla de Negocio: Cargar catálogo precargado con diagnósticos visuales comunes 
  (ej. H52.0 Hipermetropía, H52.1 Miopía, H52.2 Astigmatismo, H52.4 Presbicia); permitir selección múltiple.
- Salida / Postcondición: Datos clínicos y códigos CIE-10 asociados a la consulta.
- S-Tag Asociado: [S-TAG-INT-01] [S-TAG-RES-01]

[RF-14] Emisión e Impresión de Certificados Médicos de Aptitud Visual y Recetas
- Módulo: M3 - Historia Clínica | Prioridad MoSCoW: Must Have
- Actor Primario: Optometrista (ACT-02).
- Descripción: El sistema debe generar e imprimir directamente en formato PDF estándar: 
  1) Recetas ópticas para dispensación de lentes; 2) Certificados de aptitud visual laboral 
  y escolar con membrete oficial, datos de filiación, agudeza visual, diagnóstico y recomendaciones.
- Precondición: Consulta clínica finalizada con diagnóstico y prescripción guardados.
- Entradas: Solicitud de emisión de receta o certificado, selección de plantilla.
- Lógica / Regla de Negocio: Cargar los datos validados del examen; estampar el nombre del 
  profesional, número de registro profesional del MSP y fecha/hora UTC de emisión.
- Salida / Postcondición: Archivo PDF generado descargable e imprimible.
- S-Tag Asociado: [S-TAG-RES-01]

[RF-15] Histórico Clínico Inmutable mediante Papelera Lógica (Soft Delete)
- Módulo: M3 - Historia Clínica | Prioridad MoSCoW: Must Have
- Actor Primario: Optometrista (ACT-02) / Administrador (ACT-01).
- Descripción: El sistema debe garantizar la inmutabilidad histórica: toda consulta crea 
  un registro nuevo (prohibición de `UPDATE` destructivo). Si un registro clínico requiere 
  ser dado de baja por error insubsanable, no se eliminará físicamente de la base de datos 
  (`DELETE`); se marcará con una marca de tiempo lógica (`deleted_at`), quedando archivado 
  en una papelera clínica accesible únicamente por el Administrador.
- Precondición: Registro clínico guardado previamente.
- Entradas: Solicitud de anulación/baja de consulta clínica con motivo obligatorio.
- Lógica / Regla de Negocio: La consulta ejecutada actualiza `deleted_at = NOW()`; las 
  consultas habituales filtran `WHERE deleted_at IS NULL`. Se genera log de auditoría.
- Salida / Postcondición: Registro oculto en vistas ordinarias pero preservado para auditoría forense.
- S-Tag Asociado: [S-TAG-INT-03] [S-TAG-RES-01]

2.4 MÓDULO 4: PEDIDOS AL LABORATORIO ÓPTICO (M4)
--------------------------------------------------------------------------------

[RF-16] Emisión de Órdenes Técnicas de Taller con Aislamiento de Privacidad (LOPDP)
- Módulo: M4 - Pedidos al Laboratorio | Prioridad MoSCoW: Must Have
- Actor Primario: Optometrista (ACT-02) / Asistente (ACT-03).
- Descripción: El sistema debe generar una orden de trabajo digital para el taller óptico 
  externo (Quito/Guayaquil) conteniendo exclusivamente los datos físico-ópticos necesarios 
  para la talla y biselado (potencias de dioptrías, diseño de luna, material, tratamiento, 
  DNP y alturas). La orden debe omitir por diseño diagnósticos personales y antecedentes médicos del paciente.
- Precondición: Prescripción óptica guardada y armazón seleccionado.
- Entradas: ID de consulta, selección de laboratorio externo destinatario.
- Lógica / Regla de Negocio: Aplicar principio de minimización de datos de la LOPDP; 
  generar ticket de orden técnica con identificador único de pedido y datos de montaje.
- Salida / Postcondición: Orden técnica generada en estado "Pendiente de Envío".
- S-Tag Asociado: [S-TAG-RES-01]

[RF-17] Catálogo Parametrizable de Materiales de Lunas y Tratamientos Ópticos
- Módulo: M4 - Pedidos al Laboratorio | Prioridad MoSCoW: Must Have
- Actor Primario: Administrador (ACT-01).

[RF-20] Catálogo Comercial Simplificado para Armazones por Lotes de Precio
- Módulo: M5 - Ventas y Cobros | Prioridad MoSCoW: Must Have
- Actor Primario: Administrador (ACT-01) / Asistente (ACT-03).
- Descripción: El sistema debe permitir registrar y comercializar armazones y gafas

- Precondición: Catálogo de lotes de precios configurado.
- Entradas: Cantidad de armazones ingresados por lote, precio de venta, descripción de marca/material.

  de consolidar la venta; emitir alerta cuando el stock del lote sea inferior a 3 unidades.
- Salida / Postcondición: Stock actualizado y línea de detalle cargada en el comprobante.
- S-Tag Asociado: [S-TAG-INT-04]

[RF-21] Registro de Cobro Transaccional con Soporte de Pagos Mixtos y Anticipos/Saldos
- Módulo: M5 - Ventas y Cobros | Prioridad MoSCoW: Must Have
- Actor Primario: Asistente (ACT-03) / Administrador (ACT-01).
- Descripción: El sistema debe registrar cobros comerciales ejecutados bajo transacciones 
  ACID, permitiendo: 1) Pagos totales al contado; 2) Pagos mixtos (parte en efectivo y parte 
  por transferencia bancaria); y 3) Cobros con anticipo (ej. 50% al ordenar lunas) y saldo 
  pendiente a liquidar el día del retiro de los lentes.
- Precondición: Detalle de venta configurado (consulta, lunas, armazón).
- Entradas: Monto total, montos desglosados por forma de pago (efectivo/transferencia), monto de anticipo.
- Lógica / Regla de Negocio: Validar que `Suma(Pagos) == Monto Total` o que `Anticipo < Monto Total`. 
  Si es anticipo, calcular `Saldo = Monto Total - Anticipo`. Ejecutar inserción en bloque bajo `BEGIN TRANSACTION`.
- Salida / Postcondición: Transacción registrada, saldos actualizados y asiento creado en caja.
- S-Tag Asociado: [S-TAG-INT-04] [S-TAG-RES-02]

[RF-22] Emisión de Comprobantes Internos de Venta y Notas de Retiro
- Módulo: M5 - Ventas y Cobros | Prioridad MoSCoW: Must Have
- Actor Primario: Asistente (ACT-03) / Administrador (ACT-01).
- Descripción: El sistema debe emitir comprobantes internos impresos (recibo de caja y 
  nota de retiro de lentes) con número secuencial automático, fecha, detalle de productos/servicios, 
  desglose de pagos, anticipo cancelado y saldo pendiente. El sistema debe soportar impresión 
  térmica de punto de venta (80 mm) y formato digital PDF.
- Precondición: Cobro registrado exitosamente en el sistema.
- Entradas: ID de la transacción de venta.
- Lógica / Regla de Negocio: Formatear comprobante con tipografía optimizada para ticket térmico; 
  incluir número secuencial interno independiente de facturación SRI.
- Salida / Postcondición: Ticket térmico impreso y PDF descargable generado.
- S-Tag Asociado: [S-TAG-RES-01] [S-TAG-RES-02]

[RF-23] Cierre Diario de Caja y Arqueo Consolidado de Transacciones
- Módulo: M5 - Ventas y Cobros | Prioridad MoSCoW: Must Have
- Actor Primario: Asistente (ACT-03) / Administrador (ACT-01).
- Descripción: El sistema debe realizar el arqueo y cierre diario de caja, calculando de 
  forma automática: Saldo Inicial en Efectivo + Total Cobros en Efectivo + Total Cobros por 
  Transferencia - Total Egresos Menores Justificados = Saldo Final en Caja. Debe generar 
  un reporte de cuadre diario para supervisión del propietario.
- Precondición: Jornada laboral en curso o fin de turno.
- Entradas: Monto de saldo inicial al abrir el día, conteo de efectivo físico en gaveta al cierre.
- Lógica / Regla de Negocio: Conciliar el efectivo reportado frente al efectivo calculado por 
  el sistema; registrar diferencias (sobrantes/faltantes) y bloquear la edición de transacciones 
  del día una vez ejecutado el cierre definitivo.
- Salida / Postcondición: Registro de cierre de caja inmutable y reporte de arqueo generado.
- S-Tag Asociado: [S-TAG-INT-04] [S-TAG-RES-02]

3. ESPECIFICACIÓN FORMAL DE REQUISITOS NO FUNCIONALES (RNF)
================================================================================

Conforme a la norma ISO/IEC 25010:2023 y el marco metodológico del anteproyecto:

3.1 SUBCARACTERÍSTICAS DE SEGURIDAD (ISO/IEC 25010:2023)
- RNF-SEG-01 (Autenticidad):
  * Todas las contraseñas deben cifrarse mediante el algoritmo `bcrypt` con un costo 
    algorítmico mínimo de 12 iteraciones antes de persistir en PostgreSQL.
  * Cada petición a la API REST debe autenticarse validando la firma y vigencia temporal 
    de un token JWT emitido bajo estándar RFC 7519.

- RNF-SEG-02 (Integridad):
  * Validación dual: El 100% de los campos clínicos y numéricos deben validarse tanto en 
    el cliente (React) como en el servidor (Laravel FormRequests).
  * Restricciones a nivel de base de datos: Las tablas PostgreSQL deben implementar 
    restricciones `CHECK` para rangos dióptricos (ej. `esfera BETWEEN -25.00 AND 20.00`) y claves foráneas `ON DELETE RESTRICT`.
  * Integridad transaccional: Las operaciones de venta y cobro deben ejecutarse con nivel 
    de aislamiento `READ COMMITTED` para prevenir lecturas sucias.

- RNF-SEG-03 (Responsabilidad y No Repudio):
  * El sistema debe registrar  en la tabla `audit_logs` toda operación de creación (`CREATE`), 
    modificación (`UPDATE`) y borrado lógico (`SOFT_DELETE`) en pacientes, historias, pedidos y ventas.
  * La estructura del log capturará de forma inmutable: `id`, `user_id`, `ip_address`, 
    `event_type`, `table_name`, `record_id`, `old_values` (JSONB), `new_values` (JSONB) y `created_at` (UTC).

3.2 RENDIMIENTO, DISPONIBILIDAD Y USABILIDAD
- RNF-REN-01 (Tiempo de Respuesta): El tiempo medio de respuesta en consultas de búsqueda 
  de pacientes y guardado de refracciones debe ser inferior a 1.5 segundos en la red local.

- RNF-DIS-01 (Disponibilidad Operativa en LAN): El sistema debe operar con una disponibilidad 
  del 99.5% en la red de área local del consultorio, permitiendo continuar con consultas 
  y ventas incluso ante cortes totales del servicio de internet público.

- RNF-USA-01 (Ergonomía Visual y Usabilidad): Interfaz web progresiva (PWA) de página 
  única (SPA) limpia, eliminando ventanas flotantes MDI, optimizada para alto contraste 
  y operable con flujo ágil mediante tabulación de teclado en formularios clínicos.

  

3.3 PORTABILIDAD (leer)
- RNF-POR-01 (Compatibilidad Web): Operable de forma idéntica en navegadores modernos: 
  Google Chrome 110+, Microsoft Edge 110+, Mozilla Firefox 110+ y Safari 16+.
